# 多代理協作三種模式

《Claude Code Architect》第 12 章「平行子代理」演練筆記。

## 一覽

| 模式 | 結構 | 子任務關係 | 平行？ |
| --- | --- | --- | :-: |
| Orchestrator（主控派工彙整） | 主代理 → N 個**不同專長**子代理 → 主代理彙整 | 彼此獨立、角色不同 | ✅ |
| Pipeline（管線） | A 的輸出 → B 的輸入 → C 的輸入 | 前後相依 | ❌（循序） |
| Map-Reduce（切片平行再合併） | 同一個任務切成 N 片 → N 個**相同**子代理 → 合併 | 彼此獨立、角色相同 | ✅ |

```
Orchestrator           Pipeline              Map-Reduce
    主控                 A → B → C              切片
  ┌──┼──┐                                    ┌──┼──┐
 安全 效能 測試                              W1  W2  W3（同一個 prompt）
  └──┼──┘                                    └──┼──┘
   彙整                                        合併
```

## 1. Orchestrator（主控派工彙整）

- **適用時機**：同一份材料要從多個不同角度審查或分析，例如 code review 的安全、效能、測試三個面向，或研究時分給研究員、策略師、批評者。
- **優點**
  - 每個子代理的 context 乾淨、專注一個面向，判斷比較準
  - 可以平行跑，總時間約等於最慢的那一個
  - 子代理可以限縮工具（本章只給 Read/Grep/Glob），權限最小化
- **缺點**
  - 主代理的彙整是瓶頸：要去重、解決衝突（例如同一個問題，安全面向說 Medium、測試面向說 Critical）
  - 子代理之間不能直接溝通，交叉議題（例如 `fireAndForget` 同時是安全與測試問題）只能靠主代理合併
  - 費用約是 N 倍（本次 3 個子代理約 US$1.8）

## 2. Pipeline（前一個輸出接下一個）

- **適用時機**：步驟有明確的先後依賴，例如「需求 → 規格 → 實作 → QA → 審查」，或「抓字幕 → 摘要 → 翻譯 → 發布」。
- **優點**
  - 每一關可以把關（gate），失敗就退回上一關
  - 流程好追蹤，每一步的輸入輸出都很明確
- **缺點**
  - 不能平行，總時間是每一步相加
  - 錯誤會往下傳；上游品質差，下游全部受影響
  - 中間產物要靠檔案或 prompt 傳遞，資訊容易在交接時遺失

## 3. Map-Reduce（同任務切片平行再合併）

- **適用時機**：工作量大，但每一片做的事情一樣，例如審查 200 個檔案（每個子代理負責 20 個）、翻譯 10 章、批次摘要 50 支影片。
- **優點**
  - 可以水平擴充，切越多片越快（直到碰到 rate limit）
  - 每個 worker 用同一份 prompt，結果格式一致，合併容易
- **缺點**
  - 切片邊界可能把相關內容切開（跨檔案的呼叫關係會漏看）
  - Reduce 階段要處理重複與排序
  - 只適合「可切分」的任務

## 本章屬於哪一種？

**Orchestrator 模式。**

主代理一次派出 security-reviewer、performance-reviewer、test-coverage-reviewer 三個**不同專長**的子代理，審查**同一份** `src/`，全部回來後由主代理彙整成 `REVIEW-REPORT.md`。

- 不是 Pipeline：三個子代理之間沒有依賴，也沒有互相傳遞輸出
- 不是 Map-Reduce：沒有把 `src/` 切片，三個子代理用的也不是同一份 prompt
- 但它的執行形態是「Map（平行派出）→ Reduce（彙整）」，可以看成**以角色切分**、而不是以資料切分的 fan-out / fan-in

## 選擇原則

1. 子任務之間有依賴 → Pipeline
2. 沒有依賴，需要不同專長 → Orchestrator
3. 沒有依賴，做的事情一樣，只是量大 → Map-Reduce
4. 實務上常常混用：例如 Orchestrator 的每個子代理內部再用 Map-Reduce 切檔案，或在 Pipeline 的某一關內部平行處理
